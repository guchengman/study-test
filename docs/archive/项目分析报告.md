## 一、项目定位

**Study-Test** 是一套面向"教师—学员"场景的**多科目在线题库与考试系统**，线上体验地址为 `www.xiaoyue.shop`。核心价值主张为三点：

1. **题库 + 在线考试 + 错题本**的完整闭环学习流程；
2. **AI 自动出题 + 文档导入（Word/PDF/OCR）**降低题库建设成本；
3. **一套代码，四端覆盖**（Web / Electron 桌面 / Chrome 扩展 / Android）。

代码规模：前端约 **13,000 行**（TypeScript/TSX），后端约 **3,055 行**（JavaScript ESM），根目录含 132 个文件（其中含大量运维辅助脚本）。

## 三、系统架构

### 3.1 前端架构

采用**单页应用 + 三视图状态机**：`welcome`（欢迎/科目选择）→ `exam`（答题）→ `result`（结果）。

状态管理未引入 Redux/Zustand，而是通过 `AppProvider` 组合 **5 个自定义 Hook**，合并为单一 Context 供全局消费：

```
AppProvider
├── useAuth()          登录/注册/登出、JWT 生命周期、角色切换、EmailJS 邮箱验证
├── useToast()         轻量通知
├── useUIState()       弹窗可见性、用户管理 UI、搜索/导出状态
├── useQuestionBank()  题目、科目、错题、收藏，从 API 加载
└── useExam()          考试会话、计时器、作答、评分、错题追踪
```

**特点**：除 JWT Token 外无本地持久化，所有业务数据挂载时从 API 拉取——保证多端数据一致性，但也意味着**强依赖网络**。

关键目录：
- `services/api.ts` — 类型化 `ApiClient`，封装 fetch，自动附加 JWT 并处理 401；导出 `authApi`/`questionApi`/`subjectApi`/`practiceApi`/`syncApi`/`uploadApi`。
- `services/geminiService.ts` — AI 出题核心，采用**三级 Key 降级策略**（用户 Key → 开发构建注入 → 服务端代理）。
- `services/fileService.ts` — Word/PDF 文本抽取，PDF 无文本层时降级 OCR。
- `utils/examScoring.ts` — 纯函数评分逻辑，无 React 依赖，便于测试。

### 3.2 后端架构

Express + MySQL，ES Module。入口 `server/src/index.js` 负责加载 `.env`、CORS 白名单、挂载 `/api/*` 路由、以静态方式托管 `dist/`（SPA 回退）、并代理百度 OCR。

路由模块（`server/src/routes/`）：

| 路由 | 职责 |
|---|---|
| `auth.js` | 注册/登录、用户管理、密码重置、角色转换、访问计数、鉴权端限流 |
| `questions.js` | 题目 CRUD，含可见性作用域（自有 + 订阅共享） |
| `subjects.js` | 科目 CRUD、共享（none/all/students）、订阅、学员访问控制 |
| `practice.js` | 错题记录、收藏、学习统计 |
| `sync.js` | 数据迁移/导出 |
| `students.js` | 教师侧学员管理（批准/拒绝/移除） |
| `upload.js` | 图片上传，静态托管 `/api/uploads/` |
| `ai.js` | 服务端 Gemini 代理，内存限流（每用户每分钟 10 次），限制请求体 100KB |
| `invite-codes.js` | 邀请码管理 |

中间件 `auth.js` 提供 `authMiddleware`（多数路由必需）与 `adminMiddleware`（admin + teacher）。

## 四、数据模型（MySQL）

通过编号迁移文件演进（`001_initial_schema.sql` → `009_add_help_read.sql`），共约 10 张核心表：

| 表 | 关键字段与说明 |
|---|---|
| `users` | role（admin/teacher/student/independent）、status（active/pending）、teacher_id 外键 |
| `subjects` | id（字符串主键）、share_scope（none/all/students）、created_by |
| `questions` | type（single/multiple/programming）、options(JSON)、answer(JSON)、subject_id、created_by |
| `mistake_records` | user_id+question_id 唯一，consecutive_correct（连对 3 次视为掌握，自动移除） |
| `favorites` | user_id+question_id 唯一 |
| `study_stats` | 学习时长统计 |
| `invite_codes` | type（registration/subject）、scope、max_uses |
| `subject_subscriptions` | user_id+subject_id 唯一，status（pending/approved/rejected） |
| `subject_student_access` | 学员专属共享科目的白名单 |
| `visit_counter` | 单行访问计数器 |

**迁移机制评价**：初始 schema 用 SQL，增量用独立 JS 脚本逐个执行——朴素但可控。缺点是**无自动化迁移框架**（如 Knex/Flyway），迁移顺序需人工保证，`008_fix_schema_mismatch.sql` 的存在暗示历史上出现过 schema 漂移。

## 五、核心业务逻辑

### 5.1 题型与评分

三种题型，评分逻辑集中在纯函数 `isAnswerCorrect`：
- **单选（single）**：支持"选项字母"或"选项文本"双向匹配（A → options[0]）。
- **多选（multiple）**：排序后比较；支持字母标签到文本的映射。
- **编程（programming）**：字符串归一化比较（去空白、引号统一、转小写）后判等。

> 注：编程题采用**字符串精确匹配**而非代码执行，对答案格式敏感，容错有限——这是设计上的简化取舍。

### 5.2 科目共享模型

由 `subjects.share_scope` 三级控制：
- `none` — 私有，仅创建者可见；
- `students` — 对创建者的学员可见，可选白名单；
- `all` — 任意用户可凭邀请码订阅（自动批准）。

### 5.3 角色权限

四种角色：`admin`（全权）、`teacher`（建科目/管学员/共享）、`student`（绑定教师，见教师共享）、`independent`（自管，无教师绑定）。权限边界清晰，覆盖了典型的教培场景。

### 5.4 AI 出题的 Key 安全设计

值得肯定的一处设计：生产构建时 AI Key 被 `vite.config.ts` 的 `define` 剥离为空字符串，前端不泄露密钥；用户可在设置页填入自有 Key（存 localStorage），或走**服务端代理**（Key 仅存于服务器环境变量，带限流与体积限制）。这是**合理的密钥隔离实践**。

## 六、多端形态

| 平台 | 实现方式 | 状态 |
|---|---|---|
| Web | SPA 部署于阿里云，Nginx + Express（`nginx-study-test.conf`）| 主形态，线上运行 |
| Windows 桌面 | Electron 便携版 .exe，禁用 Node 集成、开启 context isolation | 安全配置得当 |
| Chrome 扩展 | Manifest V3，host 权限指向 `xiaoyue.shop` 与固定 IP | 轻量伴随工具 |

进程管理用 `ecosystem.config.cjs`（PM2），部署提供 `install.sh` 一键脚本（支持 `--no-prompt`/`--db-host` 等参数）与 GitHub Actions（`.github/workflows/deploy.yml`）。

## 七、优势与亮点

1. **架构清晰、职责分明**：前端 Hook 分层 + 后端路由按域拆分，新人可快速定位。
2. **纯函数评分**：`examScoring.ts` 无框架依赖，可测试性好。
3. **AI 密钥隔离到位**：三级降级 + 服务端代理限流，兼顾易用与安全。
4. **多 AI 供应商 + 多格式导入**：显著降低题库冷启动成本，产品竞争力强。
5. **完整的教培权限体系**：四角色 + 三级共享 + 邀请码，业务模型成熟。
6. **多端覆盖广**：一套核心逻辑复用到四端。
7. **文档质量高**：`CLAUDE.md`/`README.md`/`CONFIGURATION.md` 详实，降低协作门槛。

## 八、风险与改进建议

按优先级排列：

### P0（建议尽快处理）
1. **根目录严重杂乱**：132 个根文件中充斥大量一次性运维脚本（`check_env1~4.ps1`、`run_fix1~2.ps1`、`fix3.ps1`、`deploy_check1~2.ps1` 等）与临时调试文件（`analyze-quote.cjs`、`check_db1~3` 等）。建议归档到 `scripts/` 或删除，`server/src/` 下的 `check-fk.js`/`test-subjects.js` 等调试文件也应移出生产源码目录。
2. **迁移无框架化**：手工按序执行迁移风险高，`008_fix_schema_mismatch` 印证了漂移问题。建议引入统一迁移工具并将迁移纳入 CI。

### P1（中期优化）
3. **无自动化测试**：未见测试目录/框架。评分、共享权限等核心逻辑应补单元测试。
4. **强网络依赖**：前端除 JWT 外无缓存，弱网/离线体验差。可对题库做本地缓存（IndexedDB）。
5. **Chrome 扩展硬编码 IP**（`<已脱敏>`）：应改为可配置域名，避免 IP 变更失效与安全暴露。
6. **AI 限流为内存实现**：`ai.js` 的 rateLimit 用 `Map`，多实例部署时失效。建议迁移至 Redis 等共享存储。

### P2（长期演进）
7. **编程题判分能力有限**：字符串匹配无法评估代码正确性，可考虑接入沙箱执行或用 AI 辅助判分。
8. **连接池偏小**：10 连接适合小流量，规模增长时需调优。
9. **技术栈激进版本**：React 19 / Tailwind v4 较新，需关注生态兼容与稳定性。

## 九、结论

Study-Test 是一个**架构规范、功能完整、产品思路清晰**的中型全栈教培题库系统。其 AI 出题与多格式导入能力构成核心差异化优势，四角色权限与三级共享模型体现了对教培业务的深入理解，多端覆盖拓宽了使用场景。

主要短板集中在**工程化治理**层面——根目录卫生、迁移自动化、测试覆盖与部署健壮性（内存限流、硬编码 IP）。这些属于典型的"从个人/小团队项目向规范化产品演进"过程中的欠账，不影响当前可用性，但会随规模增长逐渐放大维护成本。**若计划长期迭代或团队扩张，建议优先偿还 P0 与 P1 项的技术债。**
