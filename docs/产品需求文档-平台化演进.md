## 1. 背景与愿景

### 1.1 现状

系统已具备完整的「导入 → 题库 → 练习/考试 → 判分 → 错题/收藏」闭环：

- 角色：平台管理员 / 老师 / 学生 / 独立用户（`UserRoleDomain`）
- 题型：单选、多选、编程（`QuestionType = 'single' | 'multiple' | 'programming'`）
- 内容导入：Excel / PDF / Word / OCR / 图片；公式（KaTeX）；AI 出题（多模型路由）
- 基建（2026-10 P0-P2 整改后）：验证码服务端化、EmailJS 密钥服务端持有、pino 结构化日志、判分单一可信源（SSOT，**服务端仍是双轨**：`server/src/routes/exams.js` 引用手写副本 `server/src/utils/examScoring.js`，SSOT 构建产物 `examScoring.generated.js` 目前无调用方，仅靠 13 条语料的一致性测试防漂移 → Phase 0 收敛，见 FR-110）、CI 双门禁测试
- 部署形态：**单台阿里云服务器 + PM2 单实例 + MySQL 单库**，多端封装（Web / Electron / Android / Chrome 扩展）

### 1.2 愿景

从「单个老师给自家学生用的工具」演进为**同时服务两套场景的通用学习与考试评估平台**：

| 场景 | 组织形态 | 出题者 | 应试者 |
|---|---|---|---|
| 教育 | 学校 / 培训机构 / 个人教师 | 老师 | 学生 |
| 企业 | 企业 / 部门 | 培训管理者、业务专家 | 员工 |
| 个人 | 公共域（无组织） | 用户自建 | 用户自己 |

核心抽象：**一切「可拥有题库、考试与成员关系」的单位统一为租户（Organization）**。独立用户归属于系统自动创建的隐式个人租户，所有数据模型天然带租户维度，避免两套代码路径。

### 1.3 目标（可量化）

- G1：支撑机构/企业入驻，单租户内层级「组织 → 部门/班级 → 成员」；**首个灯塔场景为企业内训**（决策 D1，部门形态优先于班级形态）
- G2：题型覆盖主流考试形态（判断/填空/简答/材料题/听力/编程判题）
- G3：峰值承载：1 万日活、2000 并发应试、单场考试 1000 人在同一分钟交卷不雪崩
- G4：权限模型可审计：跨租户数据泄露 = 0（自动化隔离测试守门）

## 2. 用户角色与权限管理

### 2.1 角色体系（三层）

```
平台层    platform_admin（平台运营）
租户层    org_admin（机构/企业管理员）
空间层    space_admin（班级/部门/共享题库的管理员，由成员晋升）
内容角色  content_author（教师/培训管理者/出题人）——同一权限档，不同场景命名
应试角色  examinee（学生/员工/个人用户）——同一权限档
只读角色  reader（家长/企业领导/审计员）——按绑定关系授予
```

- 现有 `teacher` 映射为 `content_author`，`student`/`independent` 映射为 `examinee`，向后兼容不破坏现有账号。
- 一个账号可属于多个租户、担任多个空间的不同角色（如：某老师同时是 A 机构成员 + B 企业外部出题顾问）。

**角色权威源（v0.3 新增，原 H2）**

- **`org_members.role` 为目标态唯一角色权威**。`users.role`（ENUM `admin|teacher|student|independent`）在兼容期内只读不回写，兼容期 6 个月；到期后新代码禁止读取 `users.role`，由 `org_members` 派生的兼容视图承接存量调用方。
- 服务端鉴权改造：现状 `server/src/routes/exams.js` 的 `isOwner()` 直接读 `role === 'admin' || role === 'teacher'`，`subjects.js`/`students.js`/`access.js` 同样按 `users.role` 判定 —— 这些**全部是角色权威切换的改造点**，须在 Phase 2 一并替换为 `org_members.role` + 空间归属判定，不允许出现「双权威并存且判定结果不一致」的中间态。
- 需映射的关系**不止 `teacher_id` 一条**，共四条（详见 §5.2 迁移映射表）：`users.teacher_id`（师生直连）、`subject_subscriptions`（科目订阅申请）、`subject_student_access`（科目授权）、`invite_codes.scope='students'`（「仅限该老师的学生」判定，`subjects.js` 现依赖 `teacher_id` 比对）。

### 2.2 权限矩阵（核心动作 × 角色）

| 资源/动作 | platform_admin | org_admin | space_admin | content_author | examinee | reader |
|---|:-:|:-:|:-:|:-:|:-:|:-:|
| 平台运营面板、租户管理 | ✅ | — | — | — | — | — |
| 租户内成员增删/角色分配 | ✅ | ✅ | 本空间 | — | — | — |
| 题库创建/编辑 | ✅ | 全部 | 本空间 | 自己的+被授权协作 | 自己的（个人题库） | — |
| 题目删除 | 软删权 | 全部回收站 | 本空间回收站 | 自己的题目进回收站 | 自己的 | — |
| 考试创建/编辑（draft） | ✅ | 全部 | 本空间 | 自己的 | — | — |
| 考试发布 / 开考窗口设置（`start_time`/`end_time`） | ✅ | 全部 | 本空间 | 自己的 | — | — |
| 监考（看进行中答卷 / 强制收卷 / 成绩改分） | ✅ | ✅ | 本空间 | 本考试 | — | — |
| 判分（客观题自动 / 主观题人工） | ✅ | ✅ | ✅ | 自己考试的题 | — | — |
| 入场作答（窗口内自助开考） | ✅¹ | ✅¹ | ✅¹ | ✅¹ | ✅（被指派 / 公开考试） | — |
| 查自己成绩 | ✅ | ✅ | ✅ | ✅ | ✅ | — |
| 查看他人成绩明细 | — | 租户汇总 | 本空间汇总 | 本班/群明细 | — | 绑定对象明细 |
| 成绩/题库导出 | ✅ | ✅ | 本空间 | 自己的 | 个人数据（合规自助导出） | — |
| 题库设为「共享/公开」 | — | 租户级审批 | 空间级审批 | 作者申请 | — | — |

> **¹ 语义注记（v0.3，原 H1/L1）**：v0.2 的「发起考试」一行含义模糊，既有评审据此推断「教师工作流 = 创建+发布+发起，迁移后教师无法发起自己的考试」。**该推断与实现不符**：服务端不存在「教师发起考试」这一动作，现状是 owner `POST /exams` 创建 + 置 `status='published'` 并写 `start_time/end_time`（`start_time` 为 NULL 即发布即开放），学员侧 `GET /exams/available` → `POST /exams/:id/start` 自助入场，窗口与权限校验均在服务端。因此 v0.3 将动作拆为「创建 / 发布（含开考窗口）/ 监考 / 入场作答」四步，**不给 `content_author` 增设「发起」权限**（否则等于要求实现去迁就一个不存在的动作）。
>
> 「入场作答」对管理/出题角色标 ✅，语义为**该账号作为应试者时**可被安排考试并自主开考（个人租户下自己即是 owner），**不是**代他人作答。

### 2.3 数据隔离与共享规则

1. **租户强隔离**：所有业务表携带 `org_id`；查询层强制注入租户过滤（MySQL VIEW 或应用层 QueryBuilder 约束，二选一，**实施说明见 §5.1**），并提供跨租户越权自动化测试集（列入 CI 门禁）。
2. **共享即显式授权**：题库/试卷共享通过「分享记录」（现有 `SubjectShareCode` 升级为 ACL 记录：资源 × 目标（租户/空间/人）× 权限档位（只读 / 可练习 / 可协作编辑））。
3. **家长/领导只读绑定**：reader 必须经被查看者（成年学生本人 / 员工）或其所属空间管理员的授权码绑定；绑定关系可视、可撤销。
4. **最小权限与审计**：所有写操作与导出行为落审计日志表（who / when / action / resource / org_id），pino 日志已结构化，可低成本接入。
5. **合规**：涉及未成年人（学生）与家长数据、企业员工行为数据，遵循《个人信息保护法》——采集告知、目的限定、可导出可删除（注销流程已有，需扩展到家长绑定解除、员工离职数据处置策略：默认成绩归租户，个人可带走副本）。
6. **未成年人同意主体（v0.3 明确，原评审①）**：学生为未成年人时，reader（家长）绑定须经**监护人同意链**——由所属空间管理员发起授权码并留存监护人身份与同意时间（§2.3-3 的管理员授权码路径即为此设计），不得仅以「管理员已授权」替代监护人同意记录。
7. **企业数据处理角色与 DPA（v0.3 新增，原 M10）**：企业租户场景下，企业为个人信息**处理者/控制者**、平台为**受托处理方**。Phase 2 灯塔签约前必须就位：① 数据处理协议（DPA）文本模板（处理目的/范围/期限、子处理者清单含阿里云 OSS 与邮件服务、跨境传输声明、删除与返还义务）；② 租户级数据处理记录可导出（复用 FR-206 导出 + FR-602 审计日志）。FR-603 的「入职合规考签署记录」**v1 定性为「确认记录」而非法定电子签名**（不声称满足《电子签名法》可靠电子签名要件），需法律签署的场景在 Phase 4 引入第三方电子签服务后再开放。

### 2.4 认证与账号

- 保持 JWT；增加 `token.org_id` 声明 + 租户切换端点（一人多租户时选择当前工作租户，避免重复登录）。
- 企业批量导入员工账号（Excel + 初始密码强制改密，复用现有 `password_reset` 机制）。
- 可选增强（P2 优先级）：手机验证码登录（验证码基建已在服务端，复用 purpose 扩展）。

## 3. 功能需求

优先级采用 MoSCoW：M=Must / S=Should / C=Could / W=Won't（本期不做）。

**端范围约定（v0.3 新增，原 M7）**：Web 与 Electron **共用同一 `dist/`**，Electron 仅是壳；Android（Capacitor）加载同一 Web 构建产物，因此**纯前端 + 服务端实现的 FR 默认四端自动覆盖，无需额外适配**。只有三类功能需显式标注端范围：① 依赖原生能力（录音/离线存储/后台任务）；② 依赖 Chrome 扩展的注入 UI；③ 依赖仅在部分端存在的第三方 SDK。未标注即默认「全端，无原生依赖」，不构成全端定制承诺。

**FR-109 三项修正（v0.3）**

- **（a）取消「文档 50 MB」上限，改为按 MIME 分档限大小（原 L3 前提修正）**：Excel/PDF/Word 导入在**浏览器本地解析**（`src/services/extract/xlsxExtract.ts` 用 `XLSX.read`，pdfjs-dist / mammoth 同理），**根本不经服务端**，故 v0.2 担心的「文档 50MB 与图片 5MB 共用 `upload.js` 误伤导入」不成立，PRD 不再定义文档上传上限。真正需要改的是 `server/src/routes/upload.js` 现为**单一全局 `limits.fileSize = 5 * 1024 * 1024`**：加音频前必须重构为按 MIME 子类型选择上限（ multer `limits` 回调或 `fileFilter` 内手动校验 `file.size`），且**存量超限文件无需处理（实测 0 个）**。
- **（b）95% 熔断范围白名单（原 M4）**：仅熔断「新增写入且 `resource_type ∈ {audio, image, attachment}`」的上传请求（返回 429 + 明确文案）；**存量资源读取、OSS 签名 URL 签发、小文件（<1 MB）上传、成绩导出等异步任务均不受影响**。
- **（c）磁盘压力窗口量化，M11 由高降为低（原 M11）**：实测 `server/uploads/` 共 **695 个文件 / 总计 15.2 MB / 全为 .png / 超过 5MB 的 0 个**；能击穿磁盘的是音频，而音频上传随 FR-105 在 Phase 3 才开放。所以上云前真正需要的只是 Phase 1 先上 `storage_usage` 统计 + 80%/95% 告警（接 FR-701）与单文件上限分档，**不需要把存量图片迁移提前到 Phase 2**。
- **（d）回收站文件计入口径（原 M3）**：软删（FR-107）文件在 30 天滚周期内**仍计入 `storage_usage`**，到期物理删后释放配额；租户主动「立即彻底删除」可提前释放。

| 交卷接口 P95 | < 800 ms（异步落库路径，见 4.3） |
| 可用性 | 99.5%（月不可用 < 3.6 h），计划内维护走 pm2 reload |

### 4.2 演进总原则

当前「单机 + 单 MySQL」在 500 DAU 内不会出问题；租户化/企业化后按**触发条件**分步演进，避免过度设计：

| 步骤 | 触发条件 | 动作 |
|---|---|---|
| S0 | 立即 | 应用保持无状态（已满足：JWT，无 session）；所有新表带 `org_id`；**并上 shadow schema：`organizations`（含每人自动建 PERSONAL 租户）+ 存量业务表加可空 `org_id`，新内容写入时即时赋值（创建者当前租户），查询行为没有变化**（v0.3，原 H4）；慢查询日志开起来 |
| S1 | DAU > 2000 或考试并发 > 300 | 引入 **Redis**：考试快照缓存、限流计数、分布式锁、会话级草稿缓冲 |
| S2 | 交卷尖峰出现写失败/排队 | 引入 **消息队列**（起步用 MySQL 队列表 + 轮询亦可，目标态 Redis Stream 或 RabbitMQ）：提交异步入库 |
| S3 | 单库 CPU > 60% 持续 | **读写分离**：答题流水表只读副本分流统计查询；按学期/年度**归档** answer_records |
| S4 | 单机内存/带宽瓶颈 | **多实例 + Nginx upstream** 负载均衡（PM2 cluster → 多机）；静态资源全量走 CDN |
| S5 | 判题/OCR/AI 长任务成热点 | 独立 worker 进程组（pm2 不同 app），与 API 进程隔离资源 |

**两条演进原则补充（v0.3）**

- **定时任务单例为硬约束（原 M12）**：任何周期性任务（FR-204 自动收卷、`stats_daily` 聚合、存储用量统计、预警扫描、回收站 30 天清理）**必须带分布式锁/幂等锁**，否则进入 S4 多实例后会重复执行（重复发通知、重复计费、清理竞争）。现状根本没有 cron（收卷走惰性 sweep），所以约束应在 **Phase 0 引入第一个后台任务时即生效**，而不是等 S1 有 Redis 再做（单机阶段先用 MySQL 命名锁 `GET_LOCK()` 亦可）。
- **worker 隔离提前与 S2 合并（回应评审重点②的建议）**：S5（CPU 密集任务出主进程）原排在最后，但一旦 S2 交卷队列落地，**同一批 worker 就已在跑判分**，而附录 A8 已确认现状是「单实例 fork 模式，CPU 密集判分与 API 服务抖核」。因此 **S5 的判分/OCR worker 分离应与 S2 同批落地**，否则队列只是把尖峰从 API 进程转到同一进程的下一个帧。
- **Redis（S1）触发条件可能提前**：考试并发 > 300 的阈值在 Phase 2 灯塔期就可能是现实（单场 1000 人），因此把 **S1 列为 Phase 2 前置候选**（而非默认等到 Phase 3）；未上 Redis 前，快照与草稿缓冲可先用 MySQL 表过渡，但需接受写放大的代价。

### 4.3 考试尖峰模型（最关键设计）

一场 1000 人考试的「开考前 5 分钟聚集」与「交卷时刻聚集」是系统最恶劣负载，按事件分别削平：

1. **开考（读尖峰）**
   - 试卷发布即生成不可变**快照**（snapshot JSON，含题目乱序种子 per-user）；
   - **快照内容安全白名单（v0.3，原 H6 → FR-208）**：payload **必须剔除 `answer`/`explanation`/`is_correct`**，只含题干/选项/图片音频地址/题序与 `option_order`/每人 `shuffle_seed`/分值；生成时**复用 `POST /exams/:id/start` 现有的剔除实现**（服务端已在返回前剔答案，不得另写一套），发布管线递归断言，命中即**发布失败**；
   - **快照版本规则（v0.3，原 L6）**：`exam_snapshots.version` 单调递增；考试编辑后需**重新发布才生成新版**；**存在进行中 attempt 的考试禁止编辑题集**（只能关闭/新建），已开始的 attempt 永远钉在其开考时的 version 上；
   - 快照入 Redis + 客户端预取（发布后即可提前下载，考试页只校验开始时间）；
   - 题目正文含图片/音频的走 CDN，源站不出大流量。
2. **作答期间（写碎流）**
   - 客户端草稿存 localStorage，30–60 s 增量上报到草稿缓冲（Redis，带 TTL）；
   - 服务端不做逐题实时落 MySQL。
3. **交卷（写尖峰）**
   - 交卷请求只写「提交事件」进队列（幂等键：attempt_id），毫秒级返回排队号；
   - worker 消费队列：判分（SSOT 函数，CPU 密集）→ 成绩落库 → 触发通知（通知本身再进投递队列）；
   - 目标：1000 份/分钟的吞吐，成绩 5 分钟内全部可见（可接受的最终一致性，UI 显示「判分中」）。
   - **判分中状态的承载（v0.3，原 M6）**：现状 `exam_attempts.status` 为 ENUM 仅 `in_progress|submitted|auto_submitted` 三值，**无「判分中」**。方案选定为：**扩展 ENUM 加 `scoring`**（而非从 `submission_events` 派生），原因：① UI 列表页高频读 attempt，派生需多表 JOIN；② `submission_events` 在起步阶段允许被清理而 attempt 状态必须长存；③ 幂等依旧由 `uk attempt_id` 保证。迁移需 `ALTER TABLE` 重定义 ENUM，列入 Phase 3 迁移脚本并验证存量值无损。
4. **防踩踏**
   - 调度器对「到点自动收卷」分批错峰（按 attempt_id 哈希加 0–60 s 抖动）；
   - **先拆读路径上的内嵌 sweep（v0.3 新发现补 1，见 FR-204）**：现状 `sweepExpiredAttempts()` 被 7 个入口同步调用，其中 `analysis`/`attempts` 两个入口是**全卷范围**，等于在单个 HTTP 请求里串行跑上千次事务。**任何尖峰优化均应以此为前提**，否则队列只解决了显式交卷，隐式 sweep 仍会把读接口打空。

### 4.4 统计与热数据

- 排行榜/看板**禁止实时扫答题流水大表**：写路径同步维护预聚合表（`stats_daily`：org × user × 日 × 维度），看板只读聚合表；
- streak、预警等低频扫描走每日定时任务（夜间错峰）；
- 题目/知识点引用计数在删除校验路径上读，可接受。

### 4.5 安全与权限非功能

- 跨租户越权测试集为 **CI 阻塞门禁**（对齐现有双 vitest 门禁实践）；
- **快照内容断言（v0.3，原 H6）**：递归扫描 `exam_snapshots.payload` 是否含答案字段/值，作为发布管线与 CI 的硬失败项；跨租户隔离测试集同批覆盖「学员拉取他人快照 / 未发布快照」两类越权；
- 所有列表 API 强制分页上限；导出走异步任务（防大查询打挂库）；
- 判题沙箱：容器隔离、无网络、只读 FS、限时限内存、语言版本白名单——按不可信代码对待；
- 上传管线沿用 P0 加固（MIME 双校验 + nosniff），新增音频类型走同一管线；
- 限流分层：网关层（IP 全局）→ 应用层（现有 express-rate-limit 按端点）→ 租户层（企业 API Key 配额）。

### 4.6 可观测性

- pino 结构化日志已就位：补 trace_id 贯穿（nginx → node → worker → 队列）；
- 指标：prom-client 暴露 /metrics（QPS、P95、队列深度、判分延迟、Redis 命中率），Grafana 单机起步；
- 告警底线：队列积压 > 5 min、健康检查连续失败、判分失败率 > 1%、**EmailJS 额度水位 > 80%（v0.3，原 H3）**、**单请求内 sweep 条数 > 100（补 1 的回退监控）**。

### 4.7 数据可靠性

- MySQL：每日全量备份 + binlog 增量（现有备份脚本扩展），备份异地（OSS）留存 30 天；
- 恢复演练每季度一次（备份不演练等于没有）；
- 答案提交事件队列持久化，服务重启不丢未消费提交。

### 5.1 数据隔离实施说明（v0.3 新增，原 M1 悬空引用）

§2.3-1 在 v0.2 引向不存在的「§6.2」，v0.3 改为本小节。选型结论：

- **采用应用层 QueryBuilder 约束，不用 MySQL VIEW**。理由：① 现有代码全部是 `pool.execute` 裸 SQL（`server/src/routes/*` 共 10 个路由文件），VIEW 方案需重写所有查询目标表名，改动面比加过滤子句更大；② VIEW 对写入（INSERT/UPDATE via view）限列多，考试与题库的写路径复杂；③ 现状单库，VIEW 无性能收益。
- **实施形式**：封装 `withOrg(sql, orgId)` 的统一查询助手 + 约定列表/详情类 SQL 必须走它；**禁止**在路由里直接 `pool.execute` 访问租户可见范围内的数据（ESLint 自定义规则守门，与现有 `tsc --noEmit` 门禁共存）。
- **验证**：跨租户越权测试集（§8）逐路由枚举资源 ID 型参数，断言异租户访问返回 403/404；作为 CI 阻塞门禁。
